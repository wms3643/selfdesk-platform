# 智能客服生产运行说明

本文描述当前社区版代码中已经落地的智能客服能力、必须配置的安全边界，以及上线前仍需在真实环境完成的验收项。

## 请求路由

每轮访客消息按以下顺序处理：

1. 规则层识别确定性业务意图，并提取手机号、订单号等可正则识别的槽位。
2. 如果机器人启用了意图识别，小模型返回多个业务意图；小模型结果会与规则层合并，规则层识别出的高风险意图和槽位不会被小模型覆盖。
3. 机器人设置中的意图列表会过滤未启用的业务意图；`CASUAL`、`HUMAN_TRANSFER` 和 `UNKNOWN` 始终保留，避免关闭某个业务意图后把闲聊或“转人工”误过滤。
4. Java 校验意图置信度和槽位完整性。参数不足时先追问；订单、物流和投诉只把通过校验的槽位交给业务工具。
5. 闲聊直接调用回答模型；知识问题必须检索知识库；没有可信检索结果时使用兜底话术并发布转人工事件。

业务工具失败、未配置、响应非法或超时时，系统不会让模型编造查询结果，而是进入兜底和转人工流程。复合投诉只执行投诉创建工具，避免订单或物流接口失败导致投诉根本没有创建。

用户明确要求“我要下单、创建订单、帮我买”时识别为 `ORDER_CREATE`。创建订单属于写操作，当前安全策略是转人工处理，不会凭一句话直接生成订单。“怎么下单”属于知识咨询，仍走知识库检索。若后续开放自动建单，应实现“草稿确认 → 用户二次确认 → 幂等创建”的两阶段流程，并在业务系统重新鉴权和校验库存、价格与收货信息。

## 知识库严格模式

- 知识问题的可信依据来自检索结果，低相关结果不能作为回答依据。
- 历史数据没有 `llm_score_threshold` 时按 `0.5` 处理，不再把空阈值解释为“全部召回”。
- 重排按 `sourceUid` 对齐 FAQ 和来源，避免用行的 `uid` 匹配后生成 0 分占位来源。
- `useLlmWhenKbEmpty=false` 时，知识库未配置或检索为空会拒答并转人工。
- 闲聊不受该开关影响，但模型停用时不会生成自由答案。

## 业务工具绑定

在机器人工具设置中启用 `HTTP_ENDPOINT` 绑定。默认目录包含：

- `business.order.lookup`
- `business.logistics.track`
- `business.complaint.create`

这些工具默认关闭。示例配置：

```json
{
  "key": "business.order.lookup",
  "name": "Order Lookup",
  "enabled": true,
  "bindingType": "HTTP_ENDPOINT",
  "endpoint": "https://orders.example.com/internal/bytedesk/order",
  "headers": {
    "Authorization": "${ORDER_API_TOKEN}"
  },
  "timeoutMs": 4000,
  "retryable": false,
  "idempotent": true,
  "idempotencyHeader": "Idempotency-Key",
  "maxResponseBytes": 65536,
  "responseFormat": "json",
  "metadata": {
    "intent": "ORDER_QUERY"
  }
}
```

请求只发送 `requestId`、`intent` 和 Java 校验后的 `slots`，不发送完整聊天文本。订单号、手机号只在业务槽位中出现。

### 本地订单接口联调

项目内提供默认关闭的演示订单查询接口 `/internal/demo/orders/query`，用于验证 `business.order.lookup → HTTP → 订单结果 → 回答模型` 的完整链路。启用方式：

```text
BYTEDESK_DEMO_ORDER_TOKEN=<随机测试令牌>
BYTEDESK_BUSINESS_TOOL_ALLOW_HTTP=true
BYTEDESK_BUSINESS_TOOL_ALLOW_PRIVATE_HOSTS=true
```

启动参数增加 `--bytedesk.demo-order-api.enabled=true`。启动器会把默认机器人的 `business.order.lookup` 自动配置为指向本机演示接口。示例订单号为 `A123456`，也可用手机号 `13800138000` 查询。

同一开关还会配置投诉创建工具：

```text
POST /internal/demo/complaints/create
business.complaint.create
```

投诉接口要求 `reason` 至少 6 个字符，并使用 `Idempotency-Key` 对重试去重。相同幂等键重复提交时返回同一个 `complaintNo`，响应中的 `duplicate=true`。演示记录只保存在内存中，重启后清空。

这些接口只用于本地联调，令牌错误返回 401，未知订单返回 `found=false`。生产环境必须保持 `bytedesk.demo-order-api.enabled=false`，并把订单、物流和投诉工具 endpoint 替换为企业业务系统地址。

请求上下文头包括：

```text
X-Bytedesk-Request-Id
X-Bytedesk-Thread-Uid
X-Bytedesk-Message-Uid
X-Bytedesk-Robot-Uid
X-Bytedesk-Org-Uid
X-Bytedesk-Intent
```

这些头只用于关联和审计。业务服务端必须根据签名身份、租户、坐席或访客授权重新查询订单，不能仅凭 `X-Bytedesk-Org-Uid` 放行。

## 必配环境变量

```text
BYTEDESK_BUSINESS_TOOL_ALLOWED_HOSTS=orders.example.com,logistics.example.com
BYTEDESK_BUSINESS_TOOL_ALLOW_PRIVATE_HOSTS=false
BYTEDESK_BUSINESS_TOOL_ALLOW_HTTP=false
BYTEDESK_BUSINESS_TOOL_SIGNING_SECRET=<至少 32 字节的随机密钥>
ORDER_API_TOKEN=<业务 API 令牌>
JPA_DDL_AUTO=validate   # 仅在补齐并验证 Liquibase 基线后启用
```

规则如下：

- 默认要求 HTTPS，禁止自动跟随重定向。
- 未显式允许时，禁止环回、私网、链路本地和组播地址。
- `ALLOWED_HOSTS` 可用精确主机名或 `*.example.com` 形式。
- `Authorization`、`Cookie`、`X-Api-Key` 等敏感头必须使用 `${ENV_NAME}`，不能把明文密钥写入工具 JSON。
- 敏感头环境变量缺失时工具直接失败并转人工。
- 同时限制并发请求数、连接超时、请求超时、单响应大小和整轮响应总大小。

设置签名密钥后，每个请求会携带：

```text
X-Bytedesk-Timestamp
X-Bytedesk-Nonce
X-Bytedesk-Content-SHA256
X-Bytedesk-Signature
```

签名原文为：

```text
POST
<lowercase host>
<path?query>
<unix seconds>
<nonce>
<lowercase hex sha256 of request body>
```

使用 HMAC-SHA256。业务服务端还应校验时间窗口、拒绝重复 nonce，并按幂等键去重。

## 隐私和日志

- 业务意图分类、槽位抽取以及 RAG 改写/扩展使用手机号、邮箱、订单号占位符，模型返回后再恢复受保护值；RAG 记录中也保存脱敏文本。
- 业务工具响应作为不可信数据放入隔离的 `<tool_data>` 提示区，并明确禁止执行数据中的指令。
- 同步回答不会把原始业务工具响应写入 `regenerationContext`。
- 日志不记录工具请求体、鉴权头和业务响应正文。

仍需由部署方落实数据库访问控制、消息和日志保留期限、用户删除请求、审计记录及供应商数据协议。

```text
bytedesk.ai.business.intent
bytedesk.ai.business.clarification
bytedesk.ai.business.tool.calls
bytedesk.ai.business.tool.time
bytedesk.ai.business.transfer
```

建议告警：

- 工具失败率持续升高。
- `UNKNOWN` 或澄清比例异常升高。
- 转人工率突增。
- 工具 P95 延迟超过 3 秒。
- 知识库空检索率和拒答率突增。

## 管理员仪表盘

启动服务后，管理员可以直接打开：

```text
http://127.0.0.1:9003/dashboard.html
```

页面会尝试读取同源管理后台已保存的访问令牌；也可以手动粘贴登录接口返回的 `accessToken`。令牌只保存在当前页面内存中。看板展示成员、今日新增成员、在线连接、访客记录、今日新访客、在线访客、会话、排队、消息和本次进程启动以来的 AI 请求数。

管理员也可以调用：

```text
GET /api/v1/dashboard/overview
```

接口按当前登录组织统计成员、今日新增成员、在线连接、访客记录、今日新增访客、在线访客、会话总数、今日会话、进行中会话、排队会话、消息总数、今日消息和 AI 请求数。超级管理员可通过 `orgUid` 参数查看指定组织；普通组织管理员只能查看当前组织。

管理后台原有的“运营概览”还调用以下接口，社区版后端现在也提供兼容实现：

```text
GET /api/v1/service/statistic/query
GET /api/v1/service/statistic/query/date
GET /api/v1/ticket/statistic/query/date
GET /api/v1/ai/statistic/token/query/org
GET /api/v1/ai/statistic/token/hourly
```

服务统计的数字来自客服在线状态、会话状态、会话转接状态和工单状态的当前记录。首响时长、会话时长、真正的人工接入率和满意度需要额外的审计事件或评价记录，当前接口明确把这些能力标记为不可用，不用猜测值填充。AI 用量只保留进程启动后的内存计数，历史小时趋势需要单独的用量表。

当前“用户数/流量”口径是访客记录数 `visitorRecords`、今日新访客 `newVisitorsToday` 和在线访客 `onlineVisitors`。页面浏览量 PV 没有前端埋点，接口明确返回 `pageViewsAvailable=false`。需要 PV 时应在访客 Widget 和官网页面增加匿名浏览事件上报，不能把会话数直接当作浏览量。

## AI Token 与费用统计

模型调用完成后，`TokenUsageHelper` 会发布 `LlmTokenUsageEvent`。`AiTokenUsageEventListener` 异步把输入 Token、输出 Token、提供方、模型、机器人、峰谷价格、美元费用和人民币估算写入 `bytedesk_ai_token_usage`。使用异步写入是为了避免数据库较慢时阻塞流式回答。

看板和 API 现在可以查看：

- 今日与累计输入、输出和总 Token。
- 今日与累计请求数。
- 今日与累计美元费用、人民币估算。
- 按小时聚合的 Token 和费用。
- 按提供方和模型聚合的 Token 和费用。

```text
GET /api/v1/ai/statistic/token/query/org
GET /api/v1/ai/statistic/token/hourly
GET /api/v1/ai/statistic/token/models
```

DeepSeek 价格按 2026-10-18 官方页面中的 Flash 和 Pro 输入/输出单价、UTC 工作日峰谷时段计算。来源：

```text
https://api-docs.deepseek.com/quick_start/pricing
```

Spring AI 当前只提供聚合后的 Prompt Token，不能稳定取得缓存命中和未命中明细，因此费用按“输入全部未命中缓存”的较高价格估算。人民币汇率和模型单价都可以在配置中覆盖，每一条历史记录会保存当时的单价、峰谷标记和汇率，不会因为以后改价而重算旧账：

```properties
bytedesk.ai.pricing.usd-to-cny=6.6985
bytedesk.ai.pricing.overrides[0].provider=openai
bytedesk.ai.pricing.overrides[0].model=gpt-4.1
bytedesk.ai.pricing.overrides[0].input-per-million-usd=2.00
bytedesk.ai.pricing.overrides[0].output-per-million-usd=8.00
bytedesk.ai.pricing.overrides[0].peak-multiplier=1
```

DeepSeek 的官方低谷日按 UTC 工作日判断；中国法定节假日可通过
`bytedesk.ai.pricing.deepseek-off-peak-dates[0]=2026-10-01` 这类配置补充，否则节假日会被按普通工作日估算。

目前记录的是聊天模型调用。Embedding、语音转写和图片生成没有统一接入这一事件，因此不会出现在 Token 费用中。上线后还应为用量表设置归档或按年月分区，避免长期无限增长。

## 上线门槛

以下项目必须在目标环境完成，不能由单元测试代替：

1. 使用真实订单、物流和投诉接口完成鉴权、幂等、失败重试和补偿联调。
2. 使用真实租户数据验证多租户隔离和对象级权限。
3. 用有标注的业务语料校准每个意图和槽位的精确率、召回率、拒答率。
4. 压测模型、向量检索、MySQL、Redis 和消息队列，记录 P50/P95/P99、成本和限流表现。
5. 当前 Liquibase 是增量迁移，不包含 161 个 JPA 实体的完整基线；必须从已验收生产库导出基线、在全新库执行 `JPA_DDL_AUTO=validate` 通过，并完成升级预演和回滚演练后，才能关闭 `ddl-auto=update`。
6. 验证知识库文档更新、删除、过期和重建索引后不会再被引用。
7. 完成 PII 数据地图、访问审计、保留期限和删除流程评审。
8. 使用金丝雀流量观察转人工率、投诉创建成功率、工具失败率和用户满意度。
